# DEMO_SPEC.md 格式约定

单一事实源：Demo 的一切变更先进 spec，再进代码。spec 同时是投给客户看的
「我们听懂了」的证据，以及收尾时的需求确认单。全文中文，客户看得懂的话。

每回合更新时：改动处带 `<!-- R<回合号> HH:MM -->` 注记，方便回溯是哪句话
带来的变更。

## 模板

```markdown
# <客户名> Demo Spec（<日期>）

## 目标场景
<!-- 一句话：给谁演示、证明什么。例：给售后总监演示工单智能派单，证明能替掉人肉 Excel -->

## 底座与复用
<!-- 基于哪个开源项目/模板；license；改了什么 -->

## 角色与用户
<!-- 谁在用：角色、频次、场景 -->

## 数据源
<!-- 每个数据域一行：来源（真实 API / mock）、字段来自哪（截图/OpenAPI/口述）-->
| 数据域 | 来源 | 字段依据 | 备注 |
|--------|------|----------|------|

## 页面清单
<!-- 每页一行，状态：done / wip / 占位 -->
| 页面 | 状态 | 说明 |
|------|------|------|

## 打动点
<!-- 倒排优先级：老板最想看到的那一屏排第一。每条注明来自客户哪句话 -->
1.

## 暂缓项
<!-- 现场超预算的需求：是什么、为什么缓、会后计划 -->

## 已确认 / 已否决
<!-- 客户当场的表态。否决必须带理由——理由是 Judgment Unit 的原料 -->
- ✅
- ❌ （理由：）
```

## 纪律

- 「已否决」的理由永远保留，不删除——这是 decisions.jsonl 和会后 INDUCE
  的原料；
- mock 数据必须在「数据源」表里明示，收尾时逐条向客户口头确认过；
- 打动点最多 3 条。多于 3 条说明还没问出真正的打动点（回去看 elicit.md
  的逼问句式）。
