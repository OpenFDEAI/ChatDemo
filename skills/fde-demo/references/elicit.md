# 现场提问清单（Elicitation）

方法论来自仓库的 Elicitation Protocol（SPEC.md）：观察给你 what，提问才能
拿到 why。Demo 现场的提问目标只有一个：**在最少的问题里找到打动点**——
老板看到会拍板的那一屏。

## 开场三问（定坐标）

1. 「这套系统现在谁在用？最头疼的是哪个环节？」——指着客户截图问，让客户
   自己把痛点指出来；
2. 「数据现在从哪来？是人肉搬运还是有接口？」——决定 mock 还是接真 API，
   顺手要 OpenAPI / 导出样例；
3. 「您现在用什么产品干这件事？**最像您想要的产品是哪个？**」——逼出参考系，
   直接喂给开源优先管线（oss-first.md）：有参考产品就有信息架构可借。

## 逼出打动点（挑一两句用）

- 「如果这个 Demo 只能演示一个功能，您选哪个？」
- 「下周您跟老板汇报，最想投在幕布上的是哪一屏？上面是什么数字？」
- 「过去一个月，哪件事让您觉得'要是系统能干这个就好了'？」（Critical
  Decision Method 的现场变体：从具体事件里挖判断）

## 边聊边确认（每回合穿插）

- 展示 spec diff 时：「我理解成这样，对吗？」——客户纠正的每一句都是高价值
  输入，记进 已确认/已否决；
- 客户否决时**必须追问理由**：「为什么这个不行？」——理由进 decisions.jsonl，
  这是 Judgment Unit 的原料，比需求本身值钱；
- 客户眼睛亮的瞬间，记 customer_signal，并追问：「这个为什么重要？」

## 纪律

- agent 不在客户说话时插嘴；FDE 在自然停顿处触发回合；
- 术语跟着客户走：客户叫「派工单」就不要写「任务分配」；
- 问题存量永远 ≤ 打动点缺口：已经找到打动点了就停止发散，开始收敛演示。
